## Findings and required actions

2. **Preflight must prove an actual PPO60 warmstart.** `PPOAgent.__init__` silently constructs a new default policy if the requested file is absent (`agents/sherlock/ppo_agent.py:108`), and `_check_run_dir` permits existing directories. Therefore preflight must explicitly require a new exclusive run directory, a byte-identical `start.pth`, the expected PPO60 hash/kind/stage/iteration, compatible feature/action dimensions, `arch.detach_value=true`, one policy rather than an ensemble, and finite tensors. Verify that the effective loaded config and policy/critic state match PPO60 before training. `--detach-value` would otherwise create a new critic through the branch at `scripts/ppo_train.py:297`, contrary to an unchanged-architecture warmstart. Config comparison should account explicitly for the existing `buffer_capacity=1` normalization and newly defaulted false fields; do not interpret those as an undocumented behavioral change. Root owns these metadata checks and their evidence.

3. **Correct the minibatch wording before outcomes.** The sentence calling 256/1 resource adaptations with “keine weitere fachliche Variation” is too strong. Changing minibatches from 4096 to 256 increases optimizer updates by approximately 16 times at the same number of unit samples, and can change optimization materially. The smaller rollout batch, restarted Adam and newly bound random streams also distinguish this from an exact continuation. Say that these are fixed, resource-motivated changes included in this single experiment; no gain can be attributed specifically to the opponent mix or minibatch size. The plan already correctly disclaims causal attribution and exact optimizer/RNG resumption.

4. **The trainer itself does not enforce the promised safety budget.** `cmd_ppo` has no elapsed-time, deadline, memory-pressure, finite-loss or source-hash stop. Root reports preparing a bounded launcher with 30-second checks, a 90-minute cap, first-iteration projection with 20% reserve, finite-loss checks and sustained-memory-pressure stop. Verify that launcher before admitting the job, including termination of its owned worker descendants. The first-iteration estimate must include startup/elapsed wall time as well as remaining iterations, and be compared with both the 90-minute budget and 22 October 03:15 UTC. `wr_teacher=nan` is expected; restrict numerical-failure checks to required finite losses/statistics and tensors. A monitored cap has polling granularity, so terminate sufficiently early to respect the absolute deadline.

5. **Interrupted-batch counts need honest reporting.** `ppo.csv` is flushed only after all 24 rollouts and the update complete (`scripts/ppo_train.py:321–335`). If training is stopped during a subsequent rollout/update, `24 × logged iterations` is only the confirmed completed-iteration count, not necessarily the exact number of completed games. Preserve per-game completion evidence if the bounded launcher already supports it; otherwise report a confirmed count plus the partial/unknown final batch, with the 240-game maximum. Do not invent an exact total. A normal completed ten-iteration run is unambiguous. No partial checkpoint should become a candidate.

6. **Conditional deployment blocker — both existing tools are DQN-specific.** `check_candidate_runner.verify_loaded` requires `q`, compares `agent.q/extra_q`, and instruments `Agent_x`; `build_submission` hardcodes `agents.<team>.main.Agent_x`, expects run weights under `weights/`, and checks DQN-style `env_steps>0` (`scripts/build_submission.py:40,65,100`). A PPO run instead writes `ppo_0010.pth`; its actor is `PPOAgent`, and its current `env_steps` stays zero. Passing filenames around these mismatches does not provide load proof. If development qualifies, use a deliberately reviewed PPO packaging/runner path and verify policy tensors, arch, effective config, deterministic evaluation mode, both sides and the extracted package. Preserve V3 until all fresh and integration gates pass. This is not a reason to spend time building an adapter before the candidate clears the strength gate.

## Scientific scope and evidence limits

PPO60 is a prespecified final historical checkpoint, not a new selection of the historically best PPO50. The development maps are heavily reused; treating them as a screen, requiring improvement over PPO60, and then comparing only one frozen candidate against V3 on reserved fresh maps avoids claiming independent confirmation from those known outcomes. No reward, map feature or observation-truth leakage was found in this reviewed path. `Recorder` uses the actor's observations and belief for training; evaluation's complete-point reconstruction stays outside learning. The previously documented int8 rollout/update rounding discrepancy is unchanged by this proposal and is not evidence of a new blocker from static review alone.

The seed-CSV scan is evidence about recorded CSVs, not a universal proof that a map was never used: historical PPO logs do not contain per-game seeds. Root should bind the reservation to known historical training formulas/manifests and the remote teammate's current reservations as well. CNN3's documented original PPO run uses seed 3 and therefore a distinct 210000-range block; its BC collection uses 130000-range seeds. The proposed training, fresh and audit blocks are mutually disjoint. Fresh failures, incomplete budgets or an interrupted trainer must end this candidate's qualification without extending sample sizes, switching starts, or selecting an intermediate model.

No strength, metadata, tensor-finiteness, runtime or packaging success is certified by this read-only review. Those are the root's explicit preflight and conditional execution checks. Once the above preflight conditions and wording correction are recorded, there is no further protocol objection to the single bounded continuation.
